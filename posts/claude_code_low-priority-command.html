/low-priority

觸及 session 上限後，仍能繼續工作的第三條路

Claude Code 內建指令 · AI 分享聚會速覽 · 2026
TL;DR

觸及 session 上限後，/low-priority 讓你不必等重置就能繼續跑 —— 代價是回應會排隊等餘裕算力。但它不是免費的：隨機等待若拖過 prompt cache 的存活時間，下一個 prompt 會 cache miss，該段 input 從 10% 價格跳回全額 —— 也就是那部分 token 用量暴增 約 10×（重寫 cache 達 12.5×）。

Claude Max（TTL ≈ 60 分）：影響小，多數等待仍在快取內 —— 通常可放心用。
Claude Pro（TTL ≈ 5 分）：快取易過期，peak time 難等到 capacity 時，寧可等重置也別進 low-priority。

❯ /low-priority Continue now at lower priority after reaching your session limit; run again to stop

停下等待

等 session 視窗重置後再繼續。預設行為，零成本，但工作中斷 —— 長任務、跨夜跑批時最痛。
代價：時間

/low-priority

不必等重置，立刻繼續，但請求以較低優先權排隊，回應可能較慢。前提是前面的付費路徑已用完或關閉。
代價：速度 / 優先權
隱藏成本：prompt caching 失效　THE CACHE-MISS TRAP

low-priority 每個 token 的單價不變（只是改吃 monthly limit）。真正的陷阱在別處：連續的 prompt 之間若插入隨機的等待，等待一旦超過 cache 存活時間，就會讓上一輪的 prompt cache 失效（Pro ≈ 5 分鐘、Max ≈ 60 分鐘）。cache 一旦 miss，原本只要 10% 價格的 prefix，就得重付全額。

prompt 1 → response 1 → （low-priority 隨機等待 capacity） → ⚠ cache 過期 → prompt 2 → response 2
# 正常情況下 prompt 2 的 prefix 命中 cache，只付 10%；等待拖過 TTL 後變成 cache miss，付全額。

成本試算：假設 prompt 2 重用了 prompt 1 已算過的 10 單位 input（即 prefix）。以「1 單位 = 該 prefix 未快取時的原始 input 成本」為基準：

prompt 2 的 prefix 情境計價方式成本
Cache HIT（無等待，TTL 內） 10 × 0.10（cache read） 1.0 單位
Cache MISS（等待拖過 TTL） 10 × 1.0（全額 input） 10 單位
Cache MISS + 重寫 cache 10 × 1.25（5-min write premium） 12.5 單位
差距（命中 → 未命中） 10× ~ 12.5×

採相對單位而非美元 —— 訂閱制（Pro / Max）花的是 session／monthly 額度、非逐 token 帳單。
比率依 Anthropic 官方定價：cache read = 基礎 input 的 10%，5-min cache write = 125%。

結論：low-priority 不是免費的 —— 隨機等待可能打斷 prompt caching、因 cache miss 推高實際成本。這個風險取決於方案的 TTL：
Claude Max（TTL ≈ 60 分鐘）：影響較小,多數等待都還在 cache 存活期內。 Claude Pro（TTL ≈ 5 分鐘）：cache 很容易過期,一次稍長的等待就 miss,成本上升明顯。 實務上:Pro 用戶在 peak time、難等到 capacity 時,寧可等重置也別進 low-priority。
